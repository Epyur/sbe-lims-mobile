# AGENTS.md — sbe-lims-mobile (ЛИМС Мобайл)

Мобильный клиент lab-service для планшетов испытателей: номер заявки/код
оборудования (вставленный из отсканированного QR или введённый вручную) →
форма ввода → отправка на сервер. Часть общего проекта «QR → мобильный ввод
результатов» вместе с sbe-requests (генерация/печать QR) и sbe-lims (показ QR
в заявке/на оборудовании) — см.
`docs/superpowers/specs/2026-08-27-sbe-lims-mobile-qr-design.md` в корне вольта
(`.obsidian/plugins/docs/superpowers/specs/`) и план там же
(`docs/superpowers/plans/2026-08-27-sbe-lims-mobile-qr-plan.md`).

**⚠️ Исходный дизайн (диплинк `obsidian://` + камера) не заработал на реальном
устройстве — см. v0.1.4.** Obsidian mobile не даёт доступа ни к камере, ни
к открытию по нестандартной URI-схеме из QR-сканера телефона. Текущая, рабочая
схема — плоский текстовый номер в QR, копипаст в поле плагина; фото — только
из галереи. Спека/план выше описывают ПЕРВОНАЧАЛЬНЫЙ (не сработавший) дизайн —
источник правды по факту работы сейчас — этот файл и specification.md.

**Расположение (правило 2026-08-26)**: исходники + git-репо — здесь
(`C:\Obsidian\mailers\mobile\sbe-lims-mobile\`). Собранные
`manifest.json`/`main.js`/`styles.css` копируются в
`.obsidian/plugins/sbe-lims-mobile/` (live-установка Obsidian, без git и без
исходников). Путь к sbe-core — относительный
`../../../.obsidian/plugins/sbe-core/src/...` (из `src/main.ts`; на уровень
глубже, из `src/services/`/`src/ui/`, — на один `../` больше).

## Структура

- `src/main.ts` — `SbeLimsMobilePlugin`: настройки (`apiUrl`), регистрация вьюхи +
  команды, `publishService('sbe-lims-mobile', {open})`, announceUpdate на смену
  версии. Без диплинков — обычный плагин-потребитель.
- `src/ui/mobile-lims-view.ts` — `MobileLimsView` (ItemView): главный экран (поле
  ручного ввода номера/кода — в него же вставляется скопированный из QR текст) +
  экран результатов испытания (+ пикеры фото из галереи) + экран калибровки
  оборудования (с промежуточным выбором метода при 2+ привязанных, + пикер фото).
- `src/services/lims-mobile.service.ts` — `LimsMobileService`: узкое подмножество
  вызовов lab-service (тот же паттерн, что `sbe-lims/src/services/sync.service.ts` —
  `getToken` через мост ЦУП, `assertOk` на 401/403/404, multipart для калибровки
  и `uploadFile`).
- `src/types.ts` — тримминг типов lab-service, реально нужных мобильному вводу (не
  общий пакет с sbe-lims — намеренное маленькое дублирование, см. спеку «Границы»).
- `src/styles.css` — классы `tn-lm-*` поверх дизайн-системы sbe-core.

## Ключевые решения

- **Без своего экрана входа.** Чистый потребитель `getService('sbe-apstore')` —
  как и десктопный `sbe-lims`. Если не авторизован — обычная ошибка от сервера
  (401 через `assertOk`) с текстом «войдите в ЦУП Мобайл», без дублирования UI входа.
- **QR кодирует ПРОСТОЙ ТЕКСТ (номер заявки/код оборудования), не ссылку** —
  см. v0.1.4. Испытатель сканирует ЛЮБЫМ внешним приложением телефона (у
  Obsidian mobile нет доступа к камере), копирует показанный номер, вставляет в
  текстовое поле плагина. Права по-прежнему проверяет сервер по JWT
  сканирующего испытателя — сам номер/id ничего не даёт без прав.
- **Пустой `operator_form`/`calibration_operator_form` не блокирует ввод** — fallback
  на полный список `input_parameters`/`calibration_attributes` метода (тот же
  принцип, что у аналогичного fallback в десктопном конфигураторе).
- **Фото — только из галереи**, без `capture` (см. v0.1.4) — Obsidian mobile не
  даёт доступа к камере, поэтому `<input type="file" accept="image/*">` без
  атрибута `capture` открывает обычный выбор файла/галереи.
- **Ошибка отправки формы не стирает введённые значения** — только кнопка
  «Повторить» поверх той же формы (офлайн-очередь — вне scope v1, по решению
  из спеки).
- **Бэкенд lab-service не менялся** — все вызовы идут на уже существующие,
  задеплоенные эндпоинты (`GET/POST /requests/{id}`, `GET /methods`,
  `GET /equipment`, `GET /equipment/{id}/methods`,
  `POST /equipment/{id}/calibrations`, `POST /file`).

## История работ

### 2026-08-28 — v0.1.6 (WP1 — калибровочная кривая: точки x→y + селектор оборудования)

Часть общей доработки sbe-lims WP1 (см. его AGENTS.md/спека
`docs/superpowers/specs/2026-08-28-sbe-lims-calibration-curve-design.md`) — метод РП
фиксирует НЕСКОЛЬКО калибровочных точек (расстояние→тепловой поток), а не одно число,
и результат испытания должен знать, каким именно экземпляром оборудования сделан
(если их несколько для метода).

- `types.ts`: `AttributeDataType` += `'curve'` (только у calibration_attributes — набор
  точек x→y, не одно число); новый `MethodEquipmentLink` (вся таблица method_equipment
  одним запросом, в отличие от уже существующего `EquipmentMethodLink`, привязанного к
  одному equipment_id через URL).
- `mobile-lims-view.ts`: `renderFormField` — новая ветка для `data_type==='curve'` →
  `renderCurvePointsField` (список строк x/y с +/−, стартует с двух пустых — минимум для
  линейной интерполяции; пустые/нечисловые строки не попадают в values). Задействуется
  только на экране калибровки — обычные атрибуты метода никогда не бывают `curve`.
  Экран результатов испытания (`renderResultScreen`): если у метода заявки БОЛЬШЕ ОДНОЙ
  единицы «Основного» оборудования (`listAllMethodEquipment` + `listEquipment`) —
  показывается обязательный `<select>` «Оборудование»; при ровно одной единице сервер
  резолвит её сам, поле не показывается (см. lab-service `calibration_curve.go`
  `resolveSingleMainEquipment`).
- `lims-mobile.service.ts`: `saveResult` — новый `extra.equipmentId` → `equipment_id` в
  теле запроса; новый `listAllMethodEquipment()` (`GET /api/lab/method-equipment`).
- `npx tsc --noEmit -skipLibCheck` EXIT=0, `npm run build` OK. Версия 0.1.5 → **0.1.6**.
- Собранный `main.js`/`manifest.json` скопированы в vault-плагин
  (`.obsidian/plugins/sbe-lims-mobile/`) — тот же ручной шаг деплоя, что и раньше
  (Obsidian mobile синхронизируется с этой папкой, отдельного деплой-скрипта нет).

**Баг, найден в этой же сессии (живая жалоба пользователя — форма калибровки
метода РП на планшете пустая)**: `renderCalibrationForm` — если у метода НЕТ
`calibration_attributes` (`hasFields=false`), функция раньше делала `return`
СРАЗУ, до рендера блока условий среды (`CALIBRATION_SYSTEM_FIELDS` —
температура/давление/влажность) и кнопки «Сохранить запись» — хотя по
дизайну эти поля ДОЛЖНЫ быть доступны всегда, независимо от того, настроены
ли у метода собственные атрибуты калибровки (см. комментарий у
`CALIBRATION_SYSTEM_FIELDS` в `types.ts`: «сервер принимает их... для ЛЮБОЙ
калибровки, всегда»). Метод РП как раз без настроенных
`calibration_attributes` — форма была полностью пустой (только текст
«обратитесь к администратору», без единого поля ввода). **Десктопная форма
калибровки (`sbe-lims lims-view.ts renderEquipmentCalibrationForm`) этим
багом не страдает** — там env-поля рендерятся безусловно, отдельно от
атрибутов. Исправлено: `return` убран, вместо него — информационная заметка,
рендер продолжается (env-поля/фото/submit всегда доступны). Пересобрано,
скопировано в vault-плагин.

### 2026-08-27 — v0.1.5 (системные поля результатов/калибровки — температура/давление/влажность/даты)

Часть общего фикса sbe-lims v0.2.18 (см. его AGENTS.md — принцип «ничего не
настраиваемого без права пользователя настроить» + жалоба «в форме испытателя
не выводятся стандартные поля влажность/давление/температура»).

- Экран результатов испытания: `operator_form.fields` теперь резолвится и
  против `input_parameters` (атрибуты метода), И против нового
  `RESULT_SYSTEM_FIELDS` (`types.ts` — report_date/samples_in_date/exp_date/
  amb_temp/amb_pres/amb_moist, те же id, что колонки `requests`). Системные
  значения собираются в отдельный объект (не `values`) и уходят в
  `LimsMobileService.saveResult` новым `extra`-параметром (`photoBefore`/
  `photoAfter` туда же переехали — сигнатура была позиционной, стала
  объектом: слишком много необязательных полей набралось). Появляются в форме,
  ТОЛЬКО если админ явно добавил их в operator_form.fields конфигуратора
  (десктоп, «➕ Поле формы» → раздел «Системные») — сами по себе не возникают.
- Экран калибровки: температура/давление/влажность воздуха
  (`CALIBRATION_SYSTEM_FIELDS`) показываются ВСЕГДА, без привязки к
  конфигуратору — сервер (`equipment_ext.go`) и раньше принимал их как
  отдельные поля для любой калибровки, просто клиент их не показывал/не слал;
  `createEquipmentCalibration` получил новый параметр `env`.
- `npx tsc --noEmit` EXIT=0, `npm run build` OK. lab-service: только результаты
  испытания потребовали нового бэкенд-пути (`updateRequestSystemFields`,
  задеплоено вместе с sbe-lims v0.2.18) — калибровка уже была готова.
  Версия 0.1.4 → **0.1.5**.

### 2026-08-27 — v0.1.4 (убран сканер и камера — Obsidian mobile не даёт к ним доступа; QR → простой номер)

По прямому запросу пользователя после проверки v0.1.3 на реальном планшете:
ни диплинк `obsidian://` (v0.1.0), ни встроенный сканер на `getUserMedia`
(v0.1.3) не заработали — у Obsidian mobile нет доступа к камере в принципе.
Оба подхода к «умному» сканированию оказались тупиковыми; переход на самый
простой и надёжный вариант — QR как обычный текст.

- **Убран встроенный сканер**: удалён `src/ui/qr-scanner-modal.ts`
  (`QrScannerModal`), зависимость `jsqr`, кнопка «Сканировать QR» и
  `parseDeepLink` в `mobile-lims-view.ts`.
- **Убран приём диплинка**: `registerObsidianProtocolHandler` и
  `handleDeepLink` удалены из `main.ts` — плагин больше не пытается
  открываться по `obsidian://`-ссылке ни в каком виде.
- **QR теперь кодирует простой номер** (не ссылку): `mobile-link.ts` в
  sbe-requests/sbe-lims лишился `buildMobileDeepLink` — QR рисуется прямо по
  `requestNumber(r)`/`fullRequestNumber(req)`/`eq.code`, той же строке, что
  уже печаталась подписью под QR. Любое внешнее приложение-сканер (штатная
  камера, Google Lens и т.п.) умеет показать/скопировать обычный текст — в
  отличие от нестандартной URI-схемы, которую многие сканеры не предлагают
  открыть. Испытатель вставляет скопированный номер в то же текстовое поле
  главного экрана, где раньше был только «резервный ручной ввод» — теперь это
  единственный и основной способ.
- **Фото — только из галереи**: у обоих пикеров (`renderPhotoUploadPicker`,
  `renderPhotoCapturePicker`) убран атрибут `capture="environment"` (заставлял
  открывать камеру напрямую, недоступную здесь) — остался обычный
  `<input type="file" accept="image/*">`, открывающий системный выбор
  файла/галереи. Кнопки переименованы 📷→🖼, вся механика загрузки (`POST /file`
  для результатов, multipart вместе с формой для калибровки) не изменилась.
- Главный экран: подсказка и плейсхолдер поля переписаны под новую схему
  («вставьте номер из QR или введите вручную»).
- `npx tsc --noEmit` EXIT=0, `npm run build` OK. lab-service не менялся.
  Версия 0.1.3 → **0.1.4**.

### 2026-08-27 — v0.1.3 (встроенный сканер QR + фото с камеры, НЕ прижилось — см. v0.1.4)

По прямому запросу пользователя, после того как обнаружилось, что штатная
камера Android не предлагает открыть Obsidian по `obsidian://`-ссылке из QR
(см. спеку раздел 9 — это был заранее обозначенный риск, откат на вариант B).

- **Встроенный сканер** (`src/ui/qr-scanner-modal.ts`, `QrScannerModal`):
  `jsQR` (Apache-2.0) + `getUserMedia({video: {facingMode: 'environment'}})` —
  живое видео в модалке, покадровое декодирование через `requestAnimationFrame`
  + `canvas.getImageData`, останов и освобождение камеры (`track.stop()`) сразу
  по декодированию/закрытию модалки. Декодирует ТОТ ЖЕ `obsidian://`-диплинк,
  что печатают sbe-requests/sbe-lims — просто читает его в самом плагине вместо
  ухода во внешнее приложение (`parseDeepLink` в `mobile-lims-view.ts` разбирает
  `action`/`request`/`equipment` из URL). Кнопка «📷 Сканировать QR» на главном
  экране, диплинк-обработчик (`registerObsidianProtocolHandler`) остаётся как
  есть — оба пути ведут в одни и те же `openResult`/`openCalibrate`.
- **Фото с камеры**:
  - Результаты испытания: два пикера «Фото до/после испытания»
    (`<input type="file" accept="image/*" capture="environment">` — открывает
    системную камеру напрямую, без getUserMedia) — снимок сразу грузится через
    новый `LimsMobileService.uploadFile` (`POST /api/lab/file`, multipart),
    полученный `file_url` подставляется в `photo_before`/`photo_after`
    результатов (`saveResult` расширен третьим/четвёртым параметром).
  - Калибровка: один пикер «Фото к записи калибровки» — байты держатся локально
    и уходят одним multipart-запросом вместе с остальной формой
    (`createEquipmentCalibration` расширен опциональным параметром `photo`,
    сервер уже поддерживал `file` в этом эндпоинте — клиент просто не
    прокидывал его).
- `npx tsc --noEmit` EXIT=0, `npm run build` OK. lab-service не менялся (оба
  эндпоинта — `/file` и `/equipment/{id}/calibrations` — уже существовали).
  Версия 0.1.2 → **0.1.3**.
- ⚠️ Живой доступ к камере внутри Obsidian mobile (getUserMedia) — тоже не
  проверялся на реальном планшете, это следующий шаг тестирования пользователя.

### 2026-08-27 — v0.1.2 (фикс: плагин открывался в правой панели вместо вкладки)

По прямому запросу пользователя (должно быть как на десктопе — вкладка, а не
боковая панель). Причина: `activateView` использовал
`workspace.getRightLeaf(false) ?? workspace.getLeaf('tab')` — на мобиле
`getRightLeaf` всегда находит правый drawer (даже с `split=false`), так что до
фолбэка на `getLeaf('tab')` дело не доходило. Заменено на `workspace.getLeaf(false)`
— тот же вызов, что у десктопного `sbe-lims` (main.ts `activateView`), открывает
обычную вкладку в основной области на обеих платформах.

### 2026-08-27 — v0.1.1 (фикс: плагин не публиковал себя в мост window.SBE)

Найдено пользователем при живом тестировании на Android-планшете сразу после
установки v0.1.0 через мини-магазин `sbe-mobile`: кнопка «Открыть» у ЛИМС
Мобайл в списке Сервисов падала с ошибкой **«ЦУП Мобайл: Сервис sbe-lims-mobile
недоступен. Установите и включите плагин...»**, хотя плагин был установлен и
включён. Причина — `getService(id)` в мини-магазине (как и в любом другом
ЦУП/хабе) требует, чтобы САМ плагин опубликовал себя в `window.SBE` через
`publishService(id, {open}, meta)` — этот шаг был упущен при создании плагина
(вьюха/команда/диплинк были на месте, но без публикации моста хаб физически не
может найти плагин, даже открытие напрямую с ленты работает независимо и не
задето — сама ошибка возникает только при вызове именно через хаб).

- `src/main.ts`: `publishService<SbeLimsMobileApi>('sbe-lims-mobile', {open}, meta)`
  в `onload`, `unpublishService('sbe-lims-mobile')` в `onunload` — тот же
  паттерн, что у десктопного `sbe-lims`/`sbe-lims/src/main.ts`.
- `sbe-core/src/types.ts`: новый `SbeLimsMobileApi extends SbeOpenableApi` +
  ключ `'sbe-lims-mobile'` в `SbeServiceMap` (аддитивно, другие плагины не
  пересобирались — политика 2026-08-20).
- `sbe-core/src/bridge.ts`: `getServiceName` → «ЛИМС Мобайл».
- Реестр (локальный `sbe-apstore-registry/registry.json` + сервер
  `/opt/mailers/www/registry.json` через `scp`) обновлён новыми SHA-256
  хешами v0.1.1; артефакты пересобраны и скопированы в
  `.obsidian/plugins/sbe-lims-mobile/`.
- `npx tsc --noEmit` EXIT=0, `npm run build` OK. Версия 0.1.0 → **0.1.1**.
- ⚠️ Пользователю нужно **обновить плагин на планшете** (кнопка «Обновить» в
  мини-магазине `sbe-mobile`, реестр уже отдаёт новую версию) — старая v0.1.0
  на устройстве не заработает без этого шага.
